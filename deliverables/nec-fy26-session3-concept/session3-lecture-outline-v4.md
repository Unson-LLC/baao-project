# NEC FY26 第3回 レクチャー骨子 v4

## 1. 位置づけ

第3回のテーマは、**「属人知を、組織とAIが安全に使える知識へ変えるにはどう設計するか」**。

Brainbaseの製品説明を目的にしない。企業に共通するナレッジ設計の原則を説明した後、講師自身がその考え方をどのように実装しているかを示す短いケーススタディとしてBrainbaseを紹介する。

田岡氏との個別会話や匿名案件は講義の背景理解にのみ使い、参加者向け資料には出さない。第1・2回に参加していない人、GraphやOntologyを初めて聞く管理者も単独で理解できる構成とする。

## 2. Deck Brief

- **対象**: NECのAI推進担当者、各部門の管理者・リーダー。初参加者を含む
- **形式**: 現地中心、オンライン併用を想定した90分レクチャー
- **参加人数**: 20〜30名程度を想定。ただし確定人数は未確認
- **到達点**: ナレッジ施策を「文書検索の導入」ではなく、知識の昇格、意味、責任、権限、実行統制まで含む業務設計として捉えられる
- **センターピン**: AIが企業知識を安全に使うには、情報を集めるだけでなく、知識へ育てる循環と、意味・責任・権限を伴う利用構造が必要である
- **講義後に持ち帰るもの**: 自社で最初に確認すべき5つの問いと、最初の30日で試す最小単位
- **実施しないこと**: 提出物を作るグループワーク、田岡氏の個別事例の紹介、Brainbase導入提案、AI駆動PMOの営業説明

## 3. 講義全体の二層構造

### A. 知識が育つ循環

```text
業務記録・会話・実行ログ
  ↓
候補化
  ↓
observation / insight / claim / hypothesis の抽出
  ↓
出典・所有者・公開範囲・機密性の付与
  ↓
確認・修正・承認
  ↓
用途に応じた正本への昇格
  ↓
利用結果を新しい候補として戻す
```

### B. 知識を安全に使うための構造

```text
原文・資料         : Mail / Teams / Drive / 議事録
知識へのアクセス   : RAG + Graph traversal
知識の置き場所     : Personal KG / Team・Org Graph / Skills・Runbook / Documents
意味の契約         : Ontology
責任と権限         : RACI + ACL
システム接続       : MCP
利用・実行         : Agent
承認・修正・停止   : Human Gate
```

RAG、Graph、Personal KG、Ontology、RACI、Agentを一本の成熟階段として扱わない。RAGとGraphはアクセス方法、Personal KGは知識の所有・検証範囲、Ontologyは意味の契約、RACIは責任と決裁、Agentは知識の利用者である。

## 7. 統合一枚絵の正しい構造

一本の横矢印ではなく、次の二層で描く。

### 上段：知識が育つ循環

```text
Sources
  → Raw / Candidate
  → 意味抽出・分類
  → Review / Redaction / Promotion
  → 適切な正本
  → 利用結果・実行証跡
  ↺ Candidateへ戻る
```

### 下段：知識を利用する構造

```text
RAG ─┐
Graph ├→ Context Assembly → Agent → Human Gate → MCP → Business Systems
Skills┘
```

### 横断する統制

- **Ontology**: Graphへ保存・解釈する意味、型、関係、制約を検証する
- **RACI / ACL**: 昇格、閲覧、承認、実行、通知の権限を制御する
- **Provenance / Audit**: 出典、変更、承認、実行結果を追跡する

Personal KGはGraphの後段に置かず、「適切な正本」の一つとしてTeam / Org Graph、Skills / Runbook、Documentsと並べる。

## 8. Brainbase実装例の扱い

一般概念を説明した後、次の対応だけを示す。

| 一般概念 | Brainbaseでの実装例 |
|---|---|
| Knowledge Candidate / Promotion | candidate-store / Promotion Gate |
| Personal Knowledge | Personal KG |
| Organization Facts | Graph SSOT |
| Meaning Contract | Ontology Kernel（整備中） |
| Responsibility / Decision | RACI / Decision |
| Procedure | Skills / Commands |
| Connection | MCP / Connectors |
| Execution Evidence | Automation Run / Run Receipt |

「完成した万能製品」ではなく、設計原則を自分たちで実装・検証している例として話す。Ontology Kernelは整備中であることを明示し、実装済み範囲と将来像を混同しない。

## 9. 一般化ケース

### ケース

Teamsの会話には「納期は9月20日」、Driveの計画書には「9月30日」、Mailには「顧客確認後に確定」と書かれている。

### 説明する流れ

1. RAGが三つの原文と出典を取得する
2. Graphが顧客、案件、計画書、担当者、Decisionの関係を示す
3. Ontologyが「予定」「合意済み納期」「提案中」を区別する
4. RACIが納期を確定できるAccountableを特定する
5. Agentは矛盾を隠さず、確認依頼と選択肢を作る
6. Human Gateで承認された内容だけを正本と業務システムへ戻す
7. 判断結果と根拠を新しい知識として記録する

AIが最新らしい記述を勝手に正解とせず、`未確認`を保ったまま決裁へつなぐことを主題にする。

## 10. 参加者向けの5つの診断質問

1. 回答から原文と出典へ戻れるか
2. 人、案件、文書、判断の関係が分かるか
3. 個人の経験と組織の正本を区別できているか
4. 用語の意味と、実行・承認の責任が決まっているか
5. Agentの提案を人が承認・修正・停止できるか

回答を提出させる演習にはしない。その場で自社の現在地を考える短い内省として扱う。

## 11. 最初の30日

1. 判断の食い違いが起きやすい業務を1つ選ぶ
2. 原文20件と、実際に行われた判断5件を集める
3. 個人知、共有候補、組織正本、手順の置き場所を分ける
4. Accountableを含むRACIを1組決める
5. AIには実行させず、出典提示・矛盾検知・確認依頼までを試す
6. 人の修正結果を記録し、次の候補へ戻す

最初から全社ナレッジ基盤や自律Agentを作るのではなく、知識の昇格と人の判断が一周する最小ループを検証する。

## 12. 根拠と境界

### 確認済み

- 第3回は第1・2回から独立して参加できるテーマとする
- ナレッジ、属人化、組織変革は部門横断で扱いやすいテーマである
- 管理者層を含む20〜30名程度の現地参加が想定されている
- 第2回後の会話では、第3回は提出物を作るワークを予定していない
- 個別の匿名案件は参加者に共有しない
- BrainbaseのPersonal KGは、個人の判断再現と改善ループを担い、Team / Org KGとは検証主体が異なる
- Brainbaseではraw activityをcandidate-storeとPromotion Gateを経てGraph SSOTへ昇格させる設計を採る
- RACIはGraph SSOT上の組織的事実として管理される

### 設計中・将来像

- Brainbase Ontology Kernelのcanonical version、Graph保存前guard、変更承認フロー
- Mail / Teams / Driveを含む全接続先での一貫したAgent実行

### 未確認

- 最終参加人数
- 現地とオンラインの最終構成
- 当日利用できる社内ツールとネットワーク
- 匿名化データを使ったライブデモの可否
- 質疑応答に確保できる実時間
